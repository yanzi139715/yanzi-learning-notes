在一台内置存储本来就不宽裕的 Mac 上，同时开着几个 AI 编程会话做手机 App。先是一次磁盘写满，所有会话的命令和写文件同时报 `ENOSPC`；之后又在没有新增大文件的情况下，两次突然“满盘”。

用 `du` 查占用时，几个工作副本（git worktree）里的 `node_modules` 各显示 4 GB 多，看起来像是元凶。

## 原因

**事实（第一次满盘）：**一次 iOS 原生编译就会产生几个 GB 的中间文件，叠加多个工作副本里的构建产物和各种包管理器缓存，直接把盘写满。

**事实（后两次满盘）：**真凶是同时开着 4 台模拟器和多个打包服务进程，把内存吃满，系统交换文件涨到大约 13 GB。交换文件和项目文件在同一块磁盘上，内存不够时就会直接吃掉磁盘空间。关掉两台闲置模拟器后，几十秒内可用空间从不到 1 GB 回到 6 GB 多。

**事实（误导项）：**工作副本里的 `node_modules` 是用 `cp -cR` 复制的，在 APFS 上这是“克隆”，数据块和原件共享。`du` 会照常显示 4 GB 多，但实际几乎不额外占空间。只看 `du` 找元凶会被带偏。

## 怎么做

- 开工前先看一眼数据卷剩余空间：

  ```bash
  df -h /System/Volumes/Data
  ```

  如果剩余不多，先清可以重建的东西：Xcode 的 DerivedData、各工作副本里的原生构建目录、包管理器缓存。

- 满盘但找不到大文件时，先看交换文件：

  ```bash
  sysctl vm.swapusage
  ```

  再数一数开着几台模拟器、几个 Node 或打包服务进程。

- 同一时间只让一个会话编译原生代码；模拟器同时最多开两台，用完就关：

  ```bash
  xcrun simctl shutdown all
  ```

- 工作副本里的依赖用软链接或 APFS 克隆，不要真复制；判断真实占用时不要只信 `du`。

## 适用范围与失效条件

适用于存储较小的 Mac 上做 iOS、安卓或 React Native 开发，尤其是多个会话、多个工作副本、多台模拟器同时开的场景。

磁盘空间充裕、或者内存够大不会大量换页时，问题不明显。非 APFS 文件系统上，“克隆不占空间”的说法不成立。

**未知：**“同时最多两台模拟器”这条规矩长期执行下来的效果，还没有系统统计。
